# Пользовательский сценарий и проверка результатов (финальная версия)

## 1. Основной пользовательский сценарий (как реализовано)

1. Аналитик вставляет текст ТЗ, загружает файл (`.md`/`.txt`/`.docx`) или
   выбирает демонстрационный пример.
2. (опционально) указывает провайдера LLM и ключ — либо оставляет
   офлайн-режим.
3. Запускает проверку. Пайплайн: разбор на разделы → покрытие шаблона →
   LLM-ревью по рубрике → эвристики → сборка отчёта.
4. Видит: число замечаний по критичности (блокер/существенное/
   незначительное), текстовый итог, покрытие официального шаблона МТС
   («N из 21 разделов»).
5. Разворачивает замечания (раздел, цитата, что неясно, почему важно, что
   уточнить, вопрос аналитику), фильтрует по категории.
6. Скачивает отчёт в Markdown для вставки в задачу/комментарий.

## 2. Как проверяли результат (протокол и что реально сделали)

- Прогнали инструмент на 3 реальных примерах ТЗ от кейсодателя (геопоток,
  CDR-поток, витрина-агрегат) — сначала в офлайн-режиме, затем с реальной
  LLM (Google Gemini 2.5 Flash через OpenAI-совместимый эндпоинт).
- Каждый отчёт вручную прочитан и проверен на релевантность: цитаты сверены
  с текстом документа, замечания оценены на предметность (не общая
  рекомендация) и полезность.
- По итогам ручной проверки найдено 6 конкретных дефектов инструмента
  (см. `docs/project-description-final.md`, раздел «Результаты») — все
  исправлены и повторно перепроверены тем же способом.
- Сравнение «сырая / доработанная» версия одного синтетического ТЗ
  (`examples/tz_flow_raw.md` vs `tz_flow_improved.md`) подтверждает
  чувствительность инструмента: у доработанной версии меньше замечаний и
  выше покрытие шаблона (проверяется автотестом `tests/test_pipeline.py`).

## 3. Пример найденной проблемы (реальный документ кейсодателя)

> Документ «Модуль потоковой геолокации абонентов»: раздел «Продуктовые
> метрики» указывает **«Задержка: < 1 мин»**, раздел «Нефункциональные
> требования» — **«Стриминг в реальном времени (задержка ≈ 0 сек)»**.

Инструмент нашёл это противоречие автоматически (LLM-режим, категория
«Противоречия и неоднозначные формулировки»), указал обе цитаты и
сформулировал вопрос аналитику: «Какое точное требование к задержке потока
данных?». Это ровно тот тип проблемы, который сложно поймать при беглом
чтении, но легко — при разработке (когда уже поздно).

## 4. Что подтвердилось, а что нет

| Ожидание | Результат проверки |
| --- | --- |
| Замечания привязаны к конкретной цитате, а не общие советы | Подтвердилось на всех 3 реальных документах |
| Работает без сбоев в офлайн-режиме | Подтвердилось |
| Провайдер-независимость реально работает, а не только в теории | Подтвердилось — переключение на Gemini не потребовало правок кода, только настройку Base URL в интерфейсе |
| Находит содержательные, а не только механические проблемы | Подтвердилось — 2 реальных примера противоречий между разделами (см. выше и «несоответствие часового пояса» в CDR-потоке) |
