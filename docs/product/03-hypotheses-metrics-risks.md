# Гипотезы, критерии успеха, метрики и риски (промежуточная версия)

## 1. Продуктовые гипотезы

| # | Гипотеза | Как проверяем | Статус |
| --- | --- | --- | --- |
| H1 | Инструмент находит места в ТЗ, которые реально вызывали корректировки со стороны разработки | Прогон на примерах кейсодателя, сверка с известными правками | проверяется на финале |
| H2 | Замечания понятны аналитику и не требуют доп. расшифровки (место → причина → что уточнить → вопрос) | Оценка формулировок кейсодателем по 3-балльной шкале | проверяется на финале |
| H3 | Доля «шумных» (нерелевантных) замечаний остаётся приемлемой (аналитик не тонет в ложных срабатываниях) | Разметка выдачи на примерах: релевантно / шум | проверяется на финале |
| H4 | Доменная рубрика + few-shot на корректировках даёт более предметный результат, чем «голый» промпт | A/B прогон: с рубрикой vs без, сравнение предметности | частично, на синтетике |
| H5 | Инструмент полезен и в офлайн-режиме (эвристики + покрытие шаблона) для закрытого контура | Прогон без API, оценка полезности базового отчёта | реализовано, оценка на финале |

## 2. Критерии успеха

Кейсодатель оценивает качественно. Считаем решение успешным, если на примерах ТЗ:

1. **Релевантность.** Большинство замечаний указывают на места, которые
   действительно стоит уточнить до разработки (а не «косметика»).
2. **Предметность.** Замечания привязаны к конкретному фрагменту ТЗ, а не
   являются общими советами. Целевой ориентир: доля замечаний с корректной
   цитатой из ТЗ → близко к 100%.
3. **Понятность.** Аналитик по замечанию сразу видит: где место, что не так,
   что дописать, какой вопрос задать.
4. **Помощь в решении.** По отчёту аналитик может отобрать пункты для правки ТЗ
   до передачи в разработку.
5. **Отсутствие «воды».** Инструмент не выдаёт советы, не связанные с этим ТЗ.

### Прокси-метрики (для теста без эталонного датасета)

| Метрика | Как считаем | Ориентир |
| --- | --- | --- |
| Precision@отчёт | доля релевантных замечаний в выдаче (разметка эксперта) | ≥ 0.7 |
| Recall по «известным правкам» | какую часть заранее известных проблемных мест инструмент подсветил | ≥ 0.6 |
| Доля замечаний с валидной цитатой | цитата дословно встречается в ТЗ | ≥ 0.95 |
| Понятность формулировок | средняя оценка эксперта 0/1/2 | ≥ 1.5 |
| Стабильность | пересечение замечаний между 2 прогонами одного ТЗ | ≥ 0.7 |

Метрики — ориентиры для разговора с кейсодателем, а не жёсткие пороги (в кейсе
количественный порог не задан).

## 3. Способ проверки (протокол)

1. Кейсодатель / команда готовит 3–5 примеров ТЗ (в идеале с известными
   поздними корректировками).
2. Для каждого ТЗ фиксируется список «известных проблемных мест» (ground truth
   на основе реальных правок).
3. Прогон инструмента (режим с LLM и офлайн).
4. Эксперт размечает каждое замечание: релевантно / шум; сопоставляет с ground
   truth (попал / не попал).
5. Считаются прокси-метрики выше; отдельно — субъективная оценка понятности.
6. Сравнение «сырая» vs «доработанная» версия одного ТЗ: индекс проработанности
   должен расти, число блокеров — падать.

## 4. Риски и ограничения AI-решения

| Риск | Влияние | Митигация |
| --- | --- | --- |
| Ложноположительные замечания («шум») | аналитик перестаёт доверять инструменту | критичность + сортировка; рубрика с чётким фокусом; few-shot на реальных корректировках; фильтр по категории |
| Слишком общие рекомендации при нехватке примеров | низкая ценность | обязательная цитата в схеме; отбрасывание замечаний без привязки; пополнение `correction_patterns.md` реальными правками |
| Пропуск важной проблемы (низкий recall) | ложное чувство готовности | эвристики поверх LLM; покрытие шаблона; явная формулировка «не заменяет аналитика» |
| Зависимость от качества и доступности LLM | нестабильный/недоступный результат | провайдер-независимый клиент; офлайн-режим; фиксированная температура; повтор при сбое парсинга |
| Данные ТЗ не должны уходить во внешний API (закрытый контур) | комплаенс | режим OpenAI-совместимого локального эндпоинта; полностью офлайн-режим; ключи только через `.env`/окружение |
| Разбиение на разделы ошибается на нестандартном оформлении | смещение привязки замечаний | несколько стратегий заголовков; замечание уровня «Документ в целом» как фолбэк |
| Галлюцинация цитаты | подрыв доверия | пост-проверка наличия цитаты в тексте (в плане на финал), пометка источника замечания (LLM/правило) |
| Переоценка/недооценка критичности | неверная приоритизация | веса критичности прозрачны и настраиваемы; итоговое решение за аналитиком |

### Ключевые допущения

- ТЗ подаётся как связный текст (Word/Markdown/txt), не скан.
- Информация в примерах нейтральная (без реальных полей и систем) — как заявлено
  в кейсе.
- У команды на финале будет доступ хотя бы к одному LLM (внешнему или локальному)
  для демонстрации режима с моделью.

## 5. Следующий шаг к пилоту

1. Собрать с NET 10–15 реальных ТЗ и связанные с ними корректировки → наполнить
   `correction_patterns.md` и few-shot.
2. Ввести пост-проверку цитат и авто-подсветку фрагмента в тексте ТЗ.
3. Обернуть ядро (`tz_reviewer`) в API-сервис для встраивания в рабочий процесс
   аналитика (кнопка «предревью» рядом с ТЗ).
4. Прогнать «слепой» тест с 2–3 аналитиками NET: замеряем время ревью и число
   поздних уточнений на следующих 1–2 спринтах.
5. По результатам — решение о встраивании в регламент подготовки ТЗ.
