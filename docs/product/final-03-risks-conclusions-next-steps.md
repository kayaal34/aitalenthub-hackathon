# Риски, выводы и следующий шаг к пилоту (финальная версия)

## 1. Ключевые риски и ограничения AI-решения (по итогам тестирования)

| Риск | Что показала проверка на реальных данных | Текущая митигация |
| --- | --- | --- |
| Ложноположительные/дублирующиеся замечания | Подтвердился: LLM и офлайн-правило иногда независимо находили один и тот же пробел | Дедупликация по теме находки (Kafka/HDFS/Data Catalog), а не только по точной цитате |
| Слишком общие рекомендации без привязки к документу | Не наблюдалось на 3 реальных документах — все замечания LLM-режима содержали цитату из текста | Обязательное поле `quote` в схеме ответа; замечание без него отбрасывается |
| Зависимость от одного провайдера/доступности LLM | Проверено на 2 провайдерах (проверка контракта + Google Gemini), в обоих случаях сработало без правок кода | Провайдер-независимый клиент + офлайн-режим как обязательная страховка |
| AI выдаёт вердикт о готовности документа | Обнаружено на промежуточном этапе (числовой индекс читался как вердикт) | Индекс убран из вывода; отчёт показывает только факты (число замечаний, покрытие шаблона) |
| Данные ТЗ не должны уходить во внешний API (закрытый контур) | Не тестировалось на реальных чувствительных данных (использовались только обезличенные примеры кейсодателя) | Офлайн-режим и локальные/внутренние эндпоинты поддержаны архитектурно |
| Отсутствие эталонного датасета для точных метрик качества | Подтверждено — precision/recall не измерены численно, только экспертная проверка вручную | Прокси-метрики определены (см. промежуточные материалы), измерение — в плане на пилот |

## 2. Выводы по результатам хакатона

- Гипотеза продукта подтвердилась на реальных данных кейсодателя: инструмент
  находит и механические, и содержательные проблемы (включая
  внутридокументные противоречия), а не только «косметику».
- Официальные критерии кейсодателя («Основные моменты документации») дали
  более точную и авторитетную рубрику, чем первоначальная реконструкция по
  общей инженерной интуиции, — это подтвердил разбор реальных документов.
- Провайдер-независимая архитектура — не избыточная инженерия, а
  необходимость: за время хакатона реально понадобилось переключиться между
  двумя разными LLM-провайдерами, и переключение не потребовало правок кода.
- Тестирование на реальных данных — обязательный этап, а не формальность:
  все найденные дефекты (дублирование находок, нераспознанные типы данных,
  ложные срабатывания на заголовках таблиц) проявились только на реальных
  документах кейсодателя и отсутствовали на синтетических примерах.

## 3. Следующий шаг к пилоту

1. Получить от NET реальные корректировки, которые разработчики вносили в
   ранее сданные ТЗ, — сейчас база паттернов корректировок построена на
   обобщённом отраслевом опыте, а не на фактической истории правок.
2. Добавить пост-проверку цитат (дословное совпадение с текстом ТЗ) и
   подсветку фрагмента прямо в отображаемом документе — снижает риск
   «галлюцинации» цитаты.
3. Провести измерение прокси-метрик (precision по релевантности, recall по
   известным правкам) на выборке из 5–10 реальных ТЗ с разметкой эксперта.
4. Обернуть ядро в API-сервис и предложить 2–3 аналитикам NET использовать
   инструмент как необязательный шаг перед сдачей ТЗ в разработку в течение
   1–2 спринтов; сравнить число поздних уточнений до/после.
5. По результатам пилота — решение о встраивании в регламент подготовки ТЗ.
