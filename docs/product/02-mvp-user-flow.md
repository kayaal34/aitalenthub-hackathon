# Границы MVP и пользовательский сценарий (промежуточная версия)

## 1. Основной пользовательский сценарий

**Актёр:** аналитик NET. **Цель:** снизить число замечаний, которые всплывут
после передачи ТЗ в разработку.

| Шаг | Действие пользователя | Ответ системы |
| --- | --- | --- |
| 1 | Открывает ТЗ-Ревьюер | Экран с 3 способами ввода: вставить текст / загрузить файл / взять пример |
| 2 | Вставляет текст ТЗ или загружает `.docx` / `.md` | Документ разбивается на разделы (заголовки, нумерация) |
| 3 | (опц.) выбирает провайдера/модель или режим offline | Показан итоговый режим анализа |
| 4 | Нажимает «Проверить ТЗ» | Пайплайн: покрытие шаблона → LLM-ревью по рубрике → эвристики → сборка отчёта (обычно 10–40 c) |
| 5 | Смотрит сводку: индекс готовности, число блокеров/существенных/незначительных, вердикт-ориентир | — |
| 6 | Разворачивает замечания (фильтр по категории) | По каждому: раздел, цитата, что неясно, почему важно для разработки, что уточнить, вопрос аналитику |
| 7 | Смотрит таблицу покрытия шаблона | Каких разделов ТЗ не хватает |
| 8 | Скачивает отчёт в Markdown | Файл для вставки в задачу / комментарий аналитику |
| 9 | Правит ТЗ по выбранным замечаниям, передаёт в разработку | — |

### Было / стало

| | Без инструмента | С инструментом |
| --- | --- | --- |
| Второе мнение по ТЗ | зависит от загрузки коллег | всегда, за 1–2 минуты |
| Форма замечаний | разрозненные комментарии | единый формат: место → причина → что уточнить → вопрос |
| Полнота охвата | «на что упал взгляд» | 19 доменных категорий + покрытие по шаблону |
| Момент обнаружения | часто на разработке/тесте | до передачи в разработку |

## 2. Границы MVP

### Входит

- Ввод ТЗ: вставка текста, загрузка `.md` / `.txt` / `.docx` (с таблицами), демо-примеры.
- Разбиение документа на разделы (Markdown-заголовки, нумерация, КАПС-заголовки).
- Проверка покрытия по каноническому шаблону ТЗ (17 разделов).
- LLM-ревью по доменной рубрике (19 категорий) с few-shot на паттернах корректировок.
- Офлайн-эвристики (заглушки/`TODO`, расплывчатые формулировки, поле без типа,
  расчёт без формулы, аббревиатуры без глоссария) — работают и без LLM.
- Структурированное замечание: категория, критичность (blocker/major/minor),
  раздел, цитата, суть, влияние на разработку, рекомендация, вопрос аналитику.
- Индекс готовности (0–100) и текст-ориентир — **не** вердикт.
- Отчёт: экран + выгрузка Markdown; CLI дополнительно даёт HTML и JSON.
- Провайдеры: Anthropic API, любой OpenAI-совместимый эндпоинт (OpenRouter,
  локальный vLLM/Ollama, внутренний контур), полностью офлайн-режим.

### Не входит (сознательно)

- Интеграции с Confluence и трекерами (вне скоупа хакатона).
- Автоматическое редактирование ТЗ.
- Проверка фактической правильности бизнес-логики и расчётов.
- Аутентификация, роли, история проверок, совместная работа.
- Дообучение модели; RAG по большой базе — только опционально на предоставленных
  примерах.

## 3. Экраны и состояния (MVP)

1. **Ввод** — вкладки «Вставить текст / Загрузить файл / Пример»; сайдбар с
   настройками провайдера; кнопка «Проверить ТЗ» (неактивна без текста).
2. **Обработка** — индикатор, текстовый статус этапа.
3. **Результат** —
   - строка метрик: индекс готовности, блокеры, существенные, незначительные;
   - вердикт-ориентир + текстовый итог проверки;
   - список замечаний (аккордеон, фильтр по категории, блокеры раскрыты);
   - таблица покрытия шаблона;
   - кнопка «Скачать отчёт (Markdown)».
4. **Ошибка LLM** — предупреждение + автоматический откат на эвристики и покрытие
   шаблона (результат всё равно показывается).

## 4. Формат результата (контракт)

```json
{
  "document_title": "ТЗ на витрину ...",
  "verdict": "Требуется доработка перед передачей в разработку",
  "readiness_score": 63,
  "summary": "3–6 предложений: общий результат проверки ...",
  "findings": [
    {
      "category": "incremental",
      "category_title": "Стратегия загрузки и инкремент",
      "severity": "blocker",
      "section": "4. Логика загрузки",
      "quote": "Данные грузятся инкрементально по дате.",
      "issue": "Не указано поле-приращение и обработка опоздавших записей.",
      "impact": "Разработчик выберет поле сам — риск потери строк или дублей.",
      "recommendation": "Указать поле watermark, окно перекрытия, поведение при повторном запуске.",
      "question_for_analyst": "По какому полю считаем приращение и на сколько назад перечитываем?"
    }
  ],
  "template_coverage": [ { "section": "Историчность (SCD)...", "present": false } ]
}
```

Маппинг критичности к формату из описания проекта: `high → blocker`,
`medium → major`, `low → minor`.

## 5. Что показываем на промежуточной демонстрации

- Прогон демо-ТЗ «сырой версии» → отчёт с блокерами (источник, ключ, инкремент,
  историчность) и существенными (типы, фильтры, NULL).
- Тот же поток на «доработанной версии» ТЗ → меньше замечаний, выше индекс.
- Офлайн-режим: тот же документ без API-ключа → эвристики + покрытие шаблона.
- Выгрузка Markdown-отчёта.
