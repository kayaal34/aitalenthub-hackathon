# Продуктовый бриф — ТЗ-Ревьюер (финальная версия)

## 1. Кто пользователь и какую проблему решает продукт

**Пользователь:** аналитик команды NET, который готовит ТЗ на разработку
нового потока/витрины данных и хочет получить второе мнение до передачи
документа в разработку.

**Проблема:** часть неоднозначностей и недостающей информации в ТЗ
обнаруживается уже во время разработки/тестирования — это стоит команде
повторных согласований, доработки реализации и повторного тестирования.

## 2. Ценностное предложение (уточнено по итогам тестирования)

За один прогон аналитик получает список конкретных мест ТЗ, которые
разработчик, скорее всего, поймёт неоднозначно — с цитатой, объяснением
причины и вопросом для уточнения. На реальных документах кейсодателя
инструмент показал, что умеет находить не только механические пробелы
(нет типа поля, нет ссылки на Data Catalog), но и содержательные проблемы:
**прямые противоречия внутри одного документа** (два раздела дают разные
требования к задержке; поле сдвига часового пояса описано разными типами в
разных местах). Это и есть основная ценность — то, что аналитик при беглом
чтении объёмного документа легко упускает.

## 3. Продуктовая гипотеза (после проверки)

Гипотеза «замечания, привязанные к цитате из документа, полезнее общих
советов» подтвердилась на практике: на 3 реальных ТЗ кейсодателя LLM-режим
сформировал 19–22 замечания на документ, из них по ручной проверке
подавляющее большинство — предметные и проверяемые (ссылаются на конкретную
строку/раздел), а не общие рекомендации.

## 4. Границы реализованного MVP

Реализовано: ввод ТЗ (текст/`.md`/`.txt`/`.docx`) → разбор на разделы →
проверка покрытия официального шаблона МТС (21 раздел) → LLM-ревью по
доменной рубрике (23 категории, включая 4 категории по официальным
критериям кейсодателя: сериализация, Data Catalog, NOT NULL/NULLABLE,
Kafka/HDFS-параметры, НСИ) → офлайн-эвристики как страховка при
недоступности LLM → структурированный отчёт с критичностью
(`blocker`/`major`/`minor`) и покрытием шаблона.

Не реализовано (сознательно, см. риски): пост-проверка того, что цитата
дословно есть в тексте; подсветка фрагмента в исходном документе;
измерение метрик на размеченной выборке.

## 5. Принятые решения и их влияние на реализацию

| Продуктовое решение | Влияние на реализацию |
| --- | --- |
| Не давать оценку «готовности» документа (по кейсу — решение аналитика) | Из UI и отчёта убран числовой «индекс готовности»; вместо него — факты: число замечаний по критичности + покрытие шаблона |
| Использовать официальные критерии кейсодателя, а не только общую инженерную интуицию | 4 новые категории рубрики и приоритетный раздел в базе знаний строго по присланному чек-листу «Основные моменты документации» |
| Не зависеть от одного провайдера LLM (закрытый контур, неизвестный доступ) | Провайдер-независимый клиент; проверено вживую на Google Gemini через OpenAI-совместимый эндпоинт — сработало без доработок кода |
| Всегда давать хоть какой-то результат | Офлайн-режим на эвристиках как обязательная страховка, а не опция |

## 6. Вклад AI Product

Продуктовые решения выше определили, что именно проверяет LLM (рубрика
построена вокруг официальных критериев кейсодателя, а не вокруг общих
«best practices» по инженерии данных) и что видит пользователь в первую
очередь (факты о покрытии и критичности вместо оценочного балла). Оба
решения приняты по итогам обратной связи, полученной на промежуточном этапе,
и напрямую изменили код (`rubric.py`, `report.py`, `app.py`).
