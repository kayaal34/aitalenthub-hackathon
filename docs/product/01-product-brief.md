# Продуктовый бриф — ТЗ-Ревьюер (промежуточная версия)

**Кейс:** AI-инструмент для анализа документации (МТС, продукт NET).
**Статус:** промежуточный, к финалу уточняется по результатам тестов.

---

## 1. Проблема

В продукте NET аналитики готовят технические задания (ТЗ) на разработку новых
потоков и витрин данных. Перед передачей в разработку ТЗ проходит ручное ревью:
аналитики и разработчики вычитывают объёмный текст и пытаются заранее найти
неоднозначные и неполные места.

Даже после ручной проверки часть проблем остаётся незамеченной. Тогда уточнение
требований происходит уже во время разработки или тестирования: документ
возвращается аналитику, команда повторно согласовывает требования, правит
реализацию и проводит дополнительное тестирование.

### Во что это обходится

Прямой измеримой цифры в кейсе нет, поэтому оцениваем структуру издержек, а не
абсолют. Одна «поздняя» правка требования запускает цепочку:

| Участник | Что делает повторно |
| --- | --- |
| Аналитик | разбирается в вопросе, уточняет у бизнеса, правит ТЗ, пере-согласовывает |
| Разработчик | останавливает/переделывает реализацию, ждёт ответ, повторно тестирует |
| Тестировщик | перепроверяет затронутые сценарии |

Стоимость = (число поздних уточнений на одно ТЗ) × (средняя трудоёмкость цикла
уточнения) × (число ТЗ в квартал). Инструмент бьёт по первому множителю —
переносит часть уточнений на этап до разработки, где правка стоит минуты, а не
человеко-дни.

---

## 2. Пользователь и сценарий использования

**Основной пользователь:** аналитик команды NET, который готовит ТЗ на новый
поток/витрину данных.

**Как пользуется:**
1. Готовит ТЗ (Word / Markdown / текст).
2. Загружает его в ТЗ-Ревьюер и запускает проверку.
3. Получает структурированный список потенциально проблемных мест.
4. Просматривает замечания, решает, какие действительно требуют правки.
5. Дорабатывает ТЗ и передаёт в разработку.

**Вторичные пользователи:** разработчик и тимлид — используют отчёт как быстрый
«входной чек» перед оценкой задачи.

Инструмент — дополнительное предварительное ревью. Он **не заменяет аналитика**
и **не выносит решение** о готовности документа.

---

## 3. Продуктовая гипотеза

> Если аналитик перед передачей ТЗ в разработку получит список конкретных,
> привязанных к тексту замечаний с объяснением и вопросом для уточнения, то
> он закроет значимую часть неоднозначностей заранее, и число поздних
> уточнений (во время разработки/тестирования) заметно снизится — при
> приемлемом уровне «шумных» замечаний.

Проверяем на примерах ТЗ кейсодателя: сравниваем найденное инструментом с
местами, которые реально вызывали корректировки.

---

## 4. Ценностное предложение

**Для аналитика:** за одну-две минуты — второе мнение по ТЗ с указанием, *где*
именно место, *почему* оно проблемное для разработки и *что спросить*, вместо
общих советов «добавьте деталей».

**Для команды:** меньше циклов «вернули ТЗ — пере-согласовали — переделали»,
более предсказуемый вход в разработку, единый чек-лист качества требований.

Отличие от «просто спросить у ChatGPT»: доменная рубрика для потоков и витрин
данных, проверка покрытия по шаблону ТЗ, привязка каждого замечания к цитате,
уровни критичности, работа с .docx, режим без внешнего API для закрытого контура.

---

## 5. Почему AI и почему сейчас

- Задача — понимание естественного языка и доменного контекста (не формальная
  валидация схемы), это сильная сторона LLM.
- Формулировки в ТЗ каждый раз разные — правила на регулярках покрывают только
  «механические» дефекты; смысловые неоднозначности ловит модель.
- Требование кейса — не общие советы, а привязка к конкретному фрагменту; это
  достигается промптом с рубрикой + few-shot на примерах корректировок.

## 6. Вклад AI Product и влияние на техническую реализацию

Продуктовые решения, которые задали архитектуру:

| Продуктовое решение | Как повлияло на реализацию |
| --- | --- |
| «Не общие советы, а привязка к тексту» | обязательное поле `quote` (дословная цитата) в схеме ответа; замечание без цитаты/сути отбрасывается |
| «Аналитик решает сам» | вывод — список гипотез о проблемах + вопросы, без вердикта «готово/не готово»; индекс готовности подан как ориентир |
| «Один пользователь — аналитик, сценарий за минуты» | один экран, демо-примеры в комплекте, отчёт выгружается в Markdown для вставки в задачу |
| «Закрытый контур МТС» | провайдер-независимый клиент (Anthropic / OpenAI-совместимый / локальный) + офлайн-режим на эвристиках |
| «Домен — потоки и витрины данных» | рубрика из 19 доменных категорий (источники, ключи, гранулярность, историчность/SCD, инкремент, DQ), а не общий список «неоднозначность/противоречие» |
| «Оценка полезности без эталонного датасета» | отчёт содержит покрытие шаблона + разбивку по критичности → measurable прокси-метрики для теста с кейсодателем |

## 7. Границы (что НЕ входит)

- Интеграции с Confluence и другими системами (явно вне скоупа хакатона).
- Автоматическая правка ТЗ за аналитика.
- Проверка фактической корректности бизнес-логики (только полнота и однозначность
  описания).
- Хранилище истории ревью, роли и права, многопользовательский режим.
